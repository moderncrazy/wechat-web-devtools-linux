# 自动化截图误报存储超限

## 现象与根因

`MiniProgram.screenshot()` 在原生 `saveFile` 阶段报 `saveFile:fail exceeded the maximum size of the file storage limit`。尚未进入 Node 图片文件写入或 Agent 图片读取阶段。

开发者工具的 `SimulatorFileSystemService.appendFile` 将追加后的整个文件大小传给期望增量的 `DirSizeCache.updateSize`；覆盖写入也存在完整大小重复累计。长时间运行后，缓存计数高于实际文件大小，导致截图中间文件的 `saveFile` 被错误拒绝。重启可暂时重置缓存，但没有解决累计错误。宿主机磁盘有剩余空间；`getSavedFileList` 不包含 USER_DATA_PATH 文件，空列表不能说明全部配额使用量为零。

## 修复

Linux 下追加运行时补丁，使 `DirSizeCache.getSize` 用原生 `_calcSize` 遍历实际文件元数据。绕过错误的增量计数和带节流的 `calcSize` 刷新；保留原配额及原截图调用链，不清理业务文件。代价是每次配额检查读取目录元数据，文件数量很大时需继续关注耗时。

`tools/fix-filesystem-size-cache.js` 根据原始导出及方法形状唯一定位模块，找不到或存在多个候选时明确失败。追加补丁可重复安装和更新；上游导出变化不能被旧补丁掩盖。`tools/fix-compiler.sh` 已接入。

## 验证

- 回归夹具来自开发者工具 2.02.2608080 的真实 DirSizeCache 模块。原代码在四次追加后把实际 8 字节累计为 30 字节；修复前两项行为测试失败，修复后通过。
- 覆盖追加、覆盖写、缩小、删除、真实超限、文件错误、其他平台，以及补丁唯一定位、幂等和上游变更检查。
- 远端复现仅操作本次创建的独立诊断目录。原版在诊断文件实际约 21MB 时开始拒绝追加，随后截图出现同一 saveFile 超限错误。没有删除已有业务文件。
- 补丁安装后，同一诊断文件成功增长到 71,417,737 字节；截图成功。一次性把 64 次追加放进单个 evaluate 会超过自动化 RPC 时限，因此随后独立读取实际文件大小并验证截图，没有把该 RPC 超时作为截图失败。
- 页面初始化完成后连续 20 次截图全部成功，已查看实际首页图片，文件约 71KB，保存文件列表未积累截图。
- 仅删除自己的诊断目录后，确认目录不存在，再连续 10 次截图全部成功，均为合法 PNG；截图耗时 1.216–1.644 秒、中位数 1.263 秒。此前未修复但重启后暂时正常的 40 次截图中位数 1.355 秒；负载与页面初始化存在差异，这不是严格性能基准。
- 本次相关 Node 回归共 44 项通过（其中新增截图测试 9 项），`bash -n tools/fix-compiler.sh` 和 `git diff --check` 通过。全目录 Node 通配测试中的 `asar-test.js` 依赖 Electron 的 ASAR 透明读取及本地构建产物，普通 Node 环境缺少该路径，未通过；远端镜像归档另做无网络静态校验。
